Reference Cases

Four reproducible cases that turn protocol controls into observable pass/fail conditions. Each case ships synthetic inputs — a governed and an ungoverned variant — and a zero-dependency validator, tools/codokey-check.mjs, that evaluates them. Expected outcomes are pinned in cases/*/expected.json and checked by the test suite.

What these are not. The validator reads declared configuration files. It does not connect to GitHub, GitLab, or any agent, does not scan live repositories, and a PASS is not certification. To use a case on a real system, export the equivalent settings into the same JSON shape — and remove secret values first.

  • Case A — Agent access to secrets
  • Case B — Excessive agent authority
  • Case C — AI-generated code approaching production
  • Case D — Audit reconstruction
# Node 18+, no install step
node --test tests/*.test.mjs
Case A · layers 02, 03

Agent access to secrets

Repository access is not the same thing as credential access. Whether an agent can read a secret depends on where the secret lives and on the boundary that enforces exclusion — not on whether the agent was "given the repo".

Scenario

A task agent is asked to fix a bug in a small service. Its workspace is a checkout of the repository. The checkout contains a local .env file, a placeholder key file, and an INI file with a hardcoded token — the kinds of files that commonly sit beside code. The agent can run commands (tests, scripts).

Control expectations

  • Every secret-bearing file is outside the agent's readable set (CK-KE-03).
  • The exclusion holds for subprocesses, not only the agent's file tool (CK-KE-03).
  • No production credential is in the agent environment (CK-KE-06, forbidden zone FZ-1).

Pass / fail conditions

CheckCondition
A1PASS if every file identified as secret-bearing matches a deny rule.
A2PASS if enforcement is os-sandbox or not-in-workspace; tool-level rules alone FAIL when the agent can run commands.
A3PASS if no environment variable name contains PROD.

Reproduce

node tools/codokey-check.mjs secrets-access --repo cases/a-secrets-access/repo --agent cases/a-secrets-access/agent-config.governed.json
# expect PASS

node tools/codokey-check.mjs secrets-access --repo cases/a-secrets-access/repo --agent cases/a-secrets-access/agent-config.ungoverned.json
# expect FAIL — failing A1, A2, A3

Expected outcome. governed → PASS. ungoverned → FAIL on A1 (deploy_key.pem and settings.ini readable), A2 (tool-level only), A3 (production variable present).

Real-world evidence. Agent configuration export (deny rules, sandbox setting), list of secret-bearing paths from a scan, a recorded denied read attempt, and the agent environment variable names (names only).

Limitations

  • Secret detection uses filename patterns and a simple assignment pattern; it will miss secrets in other forms and is not a substitute for a secret scanner.
  • The PROD naming heuristic is illustrative; real environments need an explicit classification of variables.
  • A PASS does not prove the agent product honors its declared configuration.

Case B · layers 03, 01

Excessive agent authority

An agent's authority should be derived from its task. Comparing what the task requires with what the credential grants turns "least privilege" from a slogan into a diff.

Scenario

A task agent must add pagination to one API and open a pull request in one repository. Two alternative grants are compared: a least-privilege grant and a typical convenience grant (all repositories, administration and workflow write, secrets read, two extra MCP tools, no expiry).

Control expectations

  • Repository access equals the task's repositories (CK-AA-05, forbidden zone FZ-2).
  • No permission exceeds what the task actions need (CK-AA-02).
  • Only declared tools are connected (CK-AA-03).
  • The credential expires within the task maximum (CK-AA-04).
  • The grant is sufficient, so the agent is not pushed toward workarounds (CK-AA-01).

Pass / fail conditions

CheckCondition
B1FAIL if repositories is "all" or lists any repository not in the task.
B2FAIL if any granted permission level exceeds the required level.
B3FAIL if any tool is not declared by the task.
B4FAIL if lifetime is missing or above the task maximum.
B5FAIL if a required permission is missing.

Reproduce

node tools/codokey-check.mjs excess-authority --task cases/b-excess-authority/task.json --grant cases/b-excess-authority/grant.least-privilege.json
# expect PASS

node tools/codokey-check.mjs excess-authority --task cases/b-excess-authority/task.json --grant cases/b-excess-authority/grant.excessive.json
# expect FAIL — failing B1, B2, B3, B4

Expected outcome. least-privilege → PASS. excessive → FAIL on B1–B4 (B5 passes: the grant is more than sufficient).

Real-world evidence. App installation or token configuration export (repositories, permissions, expiry) and the MCP/tool configuration for the agent, compared with the agent access policy entry.

Limitations

  • Declared grants only; effective permissions can be wider through team membership, inherited roles, or command execution on a privileged host.
  • The action-to-permission table is a simplification and not an authoritative platform mapping.

Case C · layers 04, 05, 01

AI-generated code approaching production

A review requirement is only meaningful if the approver is independent of the agent and of the person who asked for the change, if approval applies to the final revision, and if deployment is a separate human decision.

Scenario

An agent opens a pull request that changes application code and a deployment workflow. The case evaluates two policies (governed and ungoverned) and two histories of the same kind of change (independent approval vs. requester self-approval with a stale owner approval and an AI review-assistant approval).

Control expectations

  • Required approval excludes agent and requester and applies to the latest push (CK-RB-01).
  • Protection binds administrators (CK-RB-04).
  • Sensitive paths need code-owner review (CK-RB-02).
  • Production deployment requires an independent human reviewer; agents are not deployers (CK-DC-01, FZ-3).
  • Production secrets are scoped to the protected environment (CK-DC-02).

Pass / fail conditions

CheckCondition
C1–C3, C5–C6Policy checks: evaluate the settings themselves.
C4Change check: at least the required number of qualifying approvals on the head revision, including the required code owner.
C7Change check: a qualifying deployment approval exists when a deployment was triggered.

Reproduce

node tools/codokey-check.mjs production-path --change cases/c-production-path/change.independent-approval.json --policy cases/c-production-path/policy.governed.json
# expect PASS

node tools/codokey-check.mjs production-path --change cases/c-production-path/change.self-approved.json --policy cases/c-production-path/policy.governed.json
# expect FAIL — failing C4, C7

node tools/codokey-check.mjs production-path --change cases/c-production-path/change.independent-approval.json --policy cases/c-production-path/policy.ungoverned.json
# expect FAIL — failing C1, C2, C3, C5, C6, C7

Expected outcome. governed + independent → PASS (merge and deploy allowed). governed + self-approved → FAIL on C4, C7. ungoverned + independent → FAIL on C1, C2, C3, C5, C6, C7 even though one independent approval happened to exist.

Real-world evidence. Exported branch-protection or ruleset configuration, CODEOWNERS, environment protection settings, and the pull-request review and deployment-approval history.

Limitations

  • Models a single protected branch and environment.
  • Does not evaluate review quality — only who approved what.
  • Platform features vary by plan; see evidence register limitations.

Case D · layers 06, 01, 02

Audit reconstruction

Logs exist in most organizations; reconstruction often fails anyway because records are not linked by session, omit the delegating human, or never captured what the agent could read.

Scenario

After a suspected exposure, an investigator must answer eight questions about an agent session: who acted, for whom, when, with what scope, with which secret paths readable, what changed, who approved, and who authorized deployment. Two event exports are compared.

Control expectations

  • Each event has the required fields (CK-AM-01).
  • Each event links to a session (CK-AM-01).
  • Q1–Q8 are answerable for every session (CK-AM-01, CK-OR-02).
  • Records come from sources outside agent write access (CK-AM-02).

Pass / fail conditions

CheckCondition
D1FAIL if any event lacks a required field.
D2FAIL if any event lacks session_id.
D3FAIL if any reconstruction question cannot be answered for a session.
D4FAIL if any record is agent self-reported.

Reproduce

node tools/codokey-check.mjs audit-reconstruct --events cases/d-audit-reconstruct/events.complete.jsonl
# expect PASS

node tools/codokey-check.mjs audit-reconstruct --events cases/d-audit-reconstruct/events.incomplete.jsonl
# expect FAIL — failing D1, D2, D3, D4

Expected outcome. complete → PASS. incomplete → FAIL on D1, D2, D3, D4.

Real-world evidence. An export of one real session's records (platform audit log + agent session log), with secret values removed, mapped to the specification fields.

Limitations

  • Checks presence and linkage of fields, not their truthfulness.
  • Many agent products do not currently export "readable_secret_paths"; the specification marks this field as frequently unavailable.
