Layer 02 · Secrets Layer · Reference specification

Key Exposure

Can the agent read, emit, or move a credential?

Version
Protocol v1.1 · 2026-11-13
Scorecard controls
6 (4 critical)
Status
Codokey reference specification — not externally reviewed

Security objective

Keep credentials out of the agent's readable context and out of the repository, so that repository access does not imply credential access.

Boundary governed

The code-key boundary: the line between files and tools an agent may read (code) and the material that grants authority elsewhere (keys). Read access to a repository must not include read access to secrets that happen to be stored beside it.

Failure scenarios

Working-tree secret read
A local .env file sits in the repository directory. An agent with workspace read access includes it in context, or a test script it runs prints it to a log.
Agent-introduced hardcoding
An agent "fixes" a failing integration test by inlining a credential from an error message or example into source.
Exclusion mistaken for isolation
A tool-level ignore list hides .env from the agent's file tool, but a subprocess the agent launches (a test runner, a script) reads the file anyway.

Applicable agent capabilities

Every agent class that can read a workspace. The risk rises sharply for agents that can execute commands, because command execution reaches files indirectly.

Platform-neutral principles

  • Prefer absence over exclusion: secrets injected at runtime from a secret manager are not in the tree to be read.
  • Where files must exist, enforce exclusion at the boundary that also covers subprocesses (sandbox, OS permissions, separate machine).
  • Detection (scanning) and prevention (push protection) are separate controls; both are needed.

Implementation examples

Examples show one way to implement a control on a specific platform. They are not universally secure configurations; adapt and test them in your environment.

Known limitations

  • Pattern-based scanners detect known secret formats; custom or low-entropy secrets can pass undetected.
  • Tool-level deny rules are vendor-specific and, per vendor documentation, may not cover subprocesses or indirect reads.
  • A secret that was ever readable must be treated as exposed; exclusion added later does not undo prior exposure.

Remediation path

  1. Move secrets out of the working tree; inject at runtime (CK-KE-03).
  2. Enable server-side push protection (CK-KE-02) and secret scanning (CK-KE-01).
  3. Put production secrets in a store no agent identity can read (CK-KE-06).
  4. Define lifetimes and rotation per credential class (CK-KE-05).
  5. Run Reference Case A against your agent configuration.
