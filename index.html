The Codokey
Protocol

A six-layer reference model for governing code access, secrets, permissions, AI agents, and deployment authority. When AI can write, modify, and deploy code — the most valuable layer is no longer the code alone. It is the key that governs what the code can access, expose, change, and release.
01
Code Origin
Provenance Layer
Who authored this code? The answer determines the review obligation, audit requirement, and trust level before merge.
Was this written by a human, an AI agent, or a hybrid?
Is AI authorship documented in the commit or PR?
Does your policy require human review for AI-generated code?
02
Key Exposure
Secrets Layer
Does this code touch secrets, tokens, credentials, or signing keys? Every path to a secret is a governance decision.
Does the code read or reference environment variables?
Are API keys, access tokens, or SSH keys in scope?
Could the AI agent see secrets during its session?
03
Agent Authority
Permission Layer
What is the AI agent permitted to read, change, or execute? Undefined authority is a security gap.
What repository scope does the agent have?
Can the agent push to branches? Create PRs?
Is the agent connected to external systems via MCP?
04
Review Boundary
Human Gate Layer
Where must a human intervene before code proceeds? Without explicit gates, AI agents can create invisible paths.
Is human review required before merging AI-generated PRs?
Is there a mandatory review step for code touching secrets?
Are review requirements documented in your governance policy?
05
Deployment Control
Authority Layer
Can this code reach production? Who holds the deployment key, and under what conditions?
Is automated deployment gated by secret scanning?
Can an AI-generated change deploy without human approval?
Are production credentials separated from development environments?
06
Audit Memory
Accountability Layer
Can you reconstruct what happened, who authorized it, and what was exposed? Audit trails are governance proof.
Are AI agent actions logged with timestamps and scope?
Can you trace which agent accessed which repository and when?
Is there a record of what secrets were in scope during agent sessions?

Reference Model
Critical Reference

Secrets
Boundary

Every codebase contains keys. The question is not whether they exist — it is whether they are governed. AI agents that access repositories encounter these boundaries constantly. Below is the definitive classification of what lives inside the secrets boundary.

Critical
⚿
API Keys
X-API-KEY / Authorization: Bearer
Credentials that authenticate programmatic access to external services. A leaked API key grants an attacker full programmatic authority over the service — often irreversible without key rotation. AI agents that read codebases may encounter hardcoded API keys in configuration files, test fixtures, or commented code.
Critical
🔑
Access Tokens
OAuth / JWT / Bearer / Session
Time-limited credentials that authorize access to protected resources. Short-lived tokens still represent live attack surfaces during their validity window. AI coding assistants operating inside IDEs may inadvertently expose tokens present in open files or environment contexts.
Critical
⌨
SSH Keys
~/.ssh/id_rsa / ed25519
Cryptographic keys for authenticating to servers, git hosting, and infrastructure. Private key exposure means persistent unauthorized access until the key pair is rotated. An AI agent with filesystem read scope could access SSH key directories.
Critical
✍
Signing Keys
GPG / Code Signing / TLS Cert Keys
Keys that establish authenticity and integrity of releases, commits, or secure communications. Signing key exposure allows an attacker to produce artifacts that appear legitimate — a supply-chain attack vector of the highest severity.
High
⚙
Environment Variables
.env / process.env / os.environ
Runtime configuration that frequently contains production credentials, database URIs, and service endpoints. Environment files are commonly present in development repositories and may be inadvertently committed. AI agents operating in development contexts should never have read access to production .env files.
High
🗄
Database Credentials
DB_USER / DB_PASS / CONNECTION_STRING
Authentication credentials for database systems. Database credential exposure can lead to bulk data exfiltration. These credentials are frequently embedded in ORM configuration files, migration scripts, or legacy connection strings discovered by code-reading agents.
High
☁
Cloud Credentials
AWS_ACCESS_KEY / GCP_KEY / AZURE_CLIENT
Provider credentials for cloud infrastructure. A leaked cloud access key can expose entire infrastructure environments, storage buckets, and managed services. Cloud credential files (e.g., ~/.aws/credentials) may fall within the filesystem scope of broad-permission AI agents.
High
⬡
GitHub / Git Secrets
GITHUB_TOKEN / GH_PAT / Deploy Keys
Tokens and keys for repository access, CI/CD triggers, and deployment automation. Personal Access Tokens (PATs) with broad scopes are high-value targets. GitHub's own secret scanning initiative inside AI agents confirms this is an active and recognized risk surface.
⚠
AI Agent + Secrets = Active Governance Requirement
GitHub's MCP Server integration enables AI agents to interact with repositories, issues, pull requests, and code. When an agent operates inside a codebase that contains any of the above secret categories — even as comments, test data, or legacy configuration — the secrets boundary is active. Governance cannot be retroactive. Secret scanning, scope restrictions, and audit logging must be in place before agent sessions begin, not after a disclosure event.

Forbidden Access Zones — No Agent Class
Production Secrets
No agent should have access to production credentials, live database connections, or production signing keys under any automated workflow.
Unscoped Repository Access
Agents must operate with the minimum repository scope required. Organization-wide read access for a single-repository task is always a governance failure.
Unsupervised Deployment
No agent should have the authority to deploy to production without a human authorization gate. Automation and autonomy are different things.
